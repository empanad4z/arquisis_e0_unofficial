  Sobre la paginación (tu preocupación principal)

  Tres defensas contra que se caiga:

  1. limit con tope duro le=100 — ?limit=5000 da 422. Sin esto, un cliente pide
     todo y te tumba el proceso.
  2. LIMIT/OFFSET siempre presentes, incluso sin filtros (default 25).

  1. ¿Sequelize sería más fácil? Casi no

  const { count, rows } = await DemandHistory.findAndCountAll({ where, limit,

  1. app/schemas/filters.py (nuevo)

  Es el corazón del cambio. Un solo modelo Pydantic que declara todo lo que
  /history acepta por URL.

  Por qué un modelo y no parámetros sueltos

  query: Annotated[DemandHistoryQuery, Query()]

  Query() le dice a FastAPI "esto no es el body, sacalo del query string". Al
  ver un modelo Pydantic ahí, FastAPI recolecta todos los query params de la
  URL, arma un dict y lo valida contra el modelo. La alternativa era escribir 18
  parámetros en la firma de la función.

  alias_generator=to_camel (línea 19)

  Convierte cada nombre de campo a camelCase para la URL: received_at_from →
  ?receivedAtFrom. Así la API se ve idiomática para quien la consume, y el
  código Python mantiene snake_case. Sin esto tendrías que escribir
  Field(alias="receivedAtFrom") en cada uno de los 18 campos.

  populate_by_name=True permite además construir el modelo desde Python usando
  el nombre real (DemandHistoryQuery(received_at_from=...)), útil en tests.

  extra="forbid" (línea 23)

  El más importante en la práctica. Por defecto Pydantic ignora claves
  desconocidas. Eso significa que ?recievedAt=2025-08-08 (con el typo) pasaría
  sin filtro y te devolvería la tabla entera. Con forbid eso es un 422.

  Detalle crítico de implementación: por esto page y limit tienen que estar
  dentro del modelo. Si los dejabas como parámetros sueltos de la función,
  extra="forbid" los vería como claves desconocidas y rechazaría toda request
  que los usara.

  date vs datetime: dos semánticas distintas (líneas 41-50)

  received_at: date | None          # ?receivedAt=2025-08-08     → el día 
  completo
  received_at_from: datetime | None # ?receivedAtFrom=...T10:00  → instante 
  exacto

  El tipo declarado define el comportamiento del filtro. date no puede matchear
  por igualdad contra un TIMESTAMPTZ (ninguna fila tiene exactamente
  medianoche), así que se expande a un rango de 24h en el repositorio. El del
  enunciado (?receivedAt=2025-08-08) es el primer caso.

  El validador assume_utc (líneas 58-68)

  Tus columnas son DateTime(timezone=True) → TIMESTAMPTZ en Postgres. Si alguien
  manda ?receivedAtFrom=2025-08-08T10:00:00 sin zona, Python lo parsea como
  naive y compararlo contra una columna con zona revienta o desplaza 
  silenciosamente el resultado según el timezone del server. El validador lo
  fuerza a UTC.

  Solo aplica a los 4 campos datetime; los date no lo necesitan porque
  _day_bounds ya construye sus límites en UTC.

  SortField como Literal (línea 7)

  SortField = Literal["id", "receivedAt", "validUntil", "demand", "city",
  "type"]

  Whitelist. Si sort_by fuera un str libre, estarías metiendo input del usuario
  en un ORDER BY — vector clásico de inyección/filtración. Con Literal, Pydantic
  rechaza cualquier otra cosa con 422 antes de llegar al repositorio, y encima
  Swagger lo muestra como dropdown.

  superior es inclusivo y te comerías o duplicarías registros exactamente a
  medianoche. El SQL generado:

  -- B) ?city=Santiago&receivedAt=2025-08-08&limit=10&page=2

    AND received_at >= '2025-08-08 00:00:00+00:00'
    AND received_at <  '2025-08-09 00:00:00+00:00'

  SORTABLE_COLUMNS — segunda barrera

  Un dict de string → columna SQLAlchemy. Aunque Literal ya validó, esto
  garantiza que nunca se interpola texto crudo en el ORDER BY; solo se puede
  llegar a un objeto columna que vos declaraste.

  count() y search() en vez de list_paginated()

  Reemplacé el método viejo por dos, porque necesitás dos queries distintas
  contra el mismo WHERE: una cuenta el total (para pages) y otra trae la página.
  Ambas llaman a _build_conditions, así que no pueden desincronizarse.

  or 0 en count() porque session.scalar() tiene tipo int | None.

  El desempate en ORDER BY

  Sin esto, ordenando por receivedAt con miles de eventos insertados en lote

  distinto entre dos requests. Resultado: la página 2 repite u omite filas que
  ya viste en la página 1. El id como criterio final hace el orden total y
  determinista.

  Detalle menor que noté al compilar el SQL: con el orden por defecto queda
  ORDER BY id DESC, id DESC — redundante. Postgres lo ignora sin costo, pero es
  feo. Se arregla en dos líneas (agregar el desempate solo si sort_by != "id");

  El flujo completo de un request

  GET /history?city=Santiago&receivedAt=2025-08-08&limit=10&page=2

  1. FastAPI junta los query params y los valida contra DemandHistoryQuery.
     "2025-08-08" → date(2025,8,8), "10" → int. Si hubiera un param desconocido,
     un limit=5000, o una fecha inválida → 422 sin tocar la DB.
  2. La ruta recibe un objeto ya validado y tipado. No parsea nada.
  3. count() → SELECT count(*) ... WHERE city=... AND received_at >= ... AND < 
     ...
  4. search() → mismo WHERE + ORDER BY ... LIMIT 10 OFFSET 10
  5. Page se arma; DemandHistoryOut (con from_attributes=True) lee cada objeto
     ORM y lo vuelve JSON.

  La validación entera ocurre en el paso 1 — antes de que la base de datos vea
  nada. Esa es la parte que en Express tendrías que construir a mano con Zod.

  alias_generator=to_camel

  La coerción de tipos (lo que pasa gratis)

  Todo lo que llega por URL es string. Pydantic lo convierte según la anotación:

  input: {'limit': '10', 'page': '2', 'demand': '42.5'}
  → limit  = 10     (int)
  → page   = 2      (int)
  → demand = 42.5   (float)

  Y rechaza lo que no puede convertir:

  receivedAt=ayer → date_from_datetime_parsing: Input should be a valid date or
  datetime

  Esta es exactamente la capa que en Express te falta: ahí q.limit seguiría
  siendo el string "5000".

  El validador assume_utc (líneas 58-68)

  @field_validator("received_at_from", "received_at_to", "valid_until_from", 
  "valid_until_to")
  @classmethod
  def assume_utc(cls, value: datetime | None) -> datetime | None:
      if value is not None and value.tzinfo is None:
          return value.replace(tzinfo=timezone.utc)
      return value

  Mecánica: @field_validator recibe los nombres de los campos a los que aplica y
  corre después del parseo de cada uno. El @classmethod va debajo (Pydantic lo
  exige; si lo invertís, falla). Lo que retornás reemplaza el valor del campo.

  Por qué existe: tus columnas son DateTime(timezone=True) → TIMESTAMPTZ.
  Comparar eso contra un datetime naive rompe la query o, peor, la desplaza
  según la zona del servidor — un bug que solo aparece en producción.

  Solo rellena la zona cuando falta; si venía, la respeta:

  receivedAtFrom=2025-08-08T10:00:00        → tzinfo=utc          (rellenado)
  receivedAtFrom=2025-08-08T10:00:00-04:00  → tzinfo=TzInfo(-14400) (respetado)

  El segundo caso importa acá: si mandás horario de Chile (-04:00/-03:00),
  Postgres compara instantes absolutos correctamente sin necesidad de que vos
  conviertas nada.

  No aplica a los campos date porque esos no llegan a ser comparados
  directamente — _day_bounds() en el repositorio construye sus límites ya en
  UTC.
