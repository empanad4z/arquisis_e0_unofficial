  1. Replicar un contenedor/servicio en Docker

  Hay dos mecanismos y es importante no confundirlos:

  a) docker compose up --scale <servicio>=N (flag de CLI, no requiere tocar el
  YAML)
  docker compose up -d --scale master=3
  Compose crea N contenedores del mismo servicio, cada uno con un sufijo
  automático (proyecto-master-1, proyecto-master-2, ...).

  b) deploy.replicas dentro del servicio en el YAML
  master:
    deploy:
      replicas: 3
  Con docker compose up -d (Compose V2, sin Swarm) esto también funciona
  directamente — ya no es exclusivo de docker stack deploy como en versiones
  antiguas. Es la forma "declarativa", recomendada si el número de réplicas es
  fijo y quieres que quede versionado en el repo.

  Requisitos que rompen ahora mismo su docker-compose.yaml si intentan escalar 
  master:

  - container_name: master — un nombre fijo obliga a que exista un único
    contenedor con ese nombre. Con >1 réplica, Docker falla al crear el segundo.
    Hay que quitar container_name y dejar que Compose autogenere los nombres.
  - ports: - "8080:8000" — mapea el puerto 8000 del contenedor al puerto 8080
    del host. Dos contenedores no pueden bind-earse al mismo puerto de host, así
    que con réplicas >1 esto también falla. Opciones:
    - Usar un rango: "8080-8090:8000" (Compose asigna un puerto libre del rango
      a cada réplica).
    - O, mejor si van a poner nginx dentro del propio compose (ver punto 2), no 
      publicar el puerto al host en absoluto y dejar que nginx hable con los
      contenedores por la red interna de Docker.

  Esto no aplica a postgres (stateful, debe quedarse en 1 instancia) ni
  necesariamente a connector — conviene revisar si connector puede correr en
  paralelo sin duplicar procesamiento antes de escalarlo (según el healthcheck
  que toca un archivo, parece un conector único a una fuente de mensajes;
  replicarlo sin idempotencia podría procesar el mismo mensaje dos veces).

  2. Balanceo de carga con nginx

  El mecanismo es el bloque upstream: se define un pool de backends y luego
  proxy_pass apunta al pool en vez de a un solo host:puerto.

  upstream master_backend {
      server 127.0.0.1:8080;
      server 127.0.0.1:8081;
      server 127.0.0.1:8082;
  }

  server {
      listen 80;
      server_name api.empanad4z.me;
      location / {
          proxy_pass http://master_backend;
          ...
      }
  }

  Algoritmos disponibles (se declaran en el upstream):
  - round robin (default, sin directiva) — reparte peticiones en orden circular.
  - least_conn — envía al backend con menos conexiones activas; mejor si las
    requests tienen duración variable.
  - ip_hash — misma IP de cliente siempre va al mismo backend (sticky sessions;
    útil si hay estado en memoria del proceso).
  - weight=N en cada server para dar más tráfico a un backend que a otro.

  Dos arquitecturas posibles según dónde vive nginx, y esto es lo relevante para
  su caso porque su nginx actual corre en el host (config típica de
  /etc/nginx/sites-available/), no dentro de docker-compose:

  - Nginx en el host (su situación actual): cada réplica del contenedor master
    debe publicar un puerto de host distinto (el rango 8080-8090:8000 de
    arriba), y el upstream en nginx/api.empanad4z.me.conf lista esos puertos
    localhost explícitamente. Simple, pero hay que sincronizar manualmente
    cuántas réplicas hay vs. cuántas entradas tiene el upstream.
  - Nginx como servicio dentro de docker-compose: se agrega un servicio nginx a
    docker-compose.yaml en la misma red que master, sin publicar puertos de
    master al host. El upstream referencia el nombre del servicio (server 
    master:8000;). Aquí hay un matiz: nginx resuelve el nombre master una sola 
    vez al arrancar (vía DNS embebido de Docker en 127.0.0.11), así que si
    escalan después de que nginx ya inició, hace falta la directiva resolver 
    127.0.0.11 valid=10s; + variable en proxy_pass para que nginx re-resuelva y
    descubra las nuevas réplicas dinámicamente, en vez de reiniciar nginx cada
    vez.

  3. Cómo se especifican las réplicas junto con el balanceo

  En resumen, réplicas y balanceo son dos configuraciones separadas que deben
  mantenerse coherentes:

  1. El número de réplicas se declara en docker-compose.yaml (deploy.replicas o
     --scale).
  2. El balanceo se declara en la config de nginx (upstream), y nginx no sabe 
     automáticamente cuántas réplicas hay salvo que usen DNS dinámico con
     resolver (arquitectura containerizada) — con nginx en el host, cada vez que
     cambian el número de réplicas hay que actualizar manualmente el upstream
     con la lista de puertos.
